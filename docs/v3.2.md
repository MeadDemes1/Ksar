# Ksar 3.2 (0.3.2) - computation, manual chip choice, task-solving foundation

## What was added
1. **`/use` - choose the chip for your next message.**
   `/use basic` (alias of `standard`), `/use advanced`, `/use auto`, `/use status`.
   - Applies to exactly one real message, then disappears. Commands (`/why`, `/chip`, `/tools`, ...) never use it up.
   - Beats complexity routing and `performance_priority`, but never the RAM check.
   - Checked when you type it (configured? installed in Ollama? fits in free RAM?) and again when the message is sent.
     An unusable chip never creates an override. If it becomes unusable in between, Ksar says why and does NOT answer
     with another chip; the override is used up, nothing is recorded, and you can send the message again.
   - The Idle/Light chip is refused: it is for background work only.
2. **`calc.evaluate` - a deterministic calculator tool** (pure Python standard library, no `eval`/`exec`).
3. **Structural complexity routing** (`ksar/router.py`) instead of keywords + length, still with no model call.
4. **Task-solving workflow** for numeric/programming problems: exact calculator results, a short work-order in the
   instructions, honest labelling of calculated / estimated / tested.
5. **Diagnostics:** `/why`, a one-line footer after each answer, `ksar_data/logs/routing.jsonl`.
6. **Bug fix:** the idle worker (0.3.1) skipped its first "what is loaded?" check on machines up for less than a minute.

## How it works
### The calculator
`calc.evaluate(expression | expressions)`; several expressions may be given at once, separated by `;` or new lines.
- Parsed with `ast.parse(mode="eval")` and evaluated by a whitelist walker. Allowed: numbers, `+ - * / // % ** ^`
  (`^` means power), parentheses, unary signs, constants `pi e tau`, and the functions
  `abs sqrt cbrt exp ln log log2 log10 sin cos tan asin acos atan atan2 sinh cosh tanh degrees radians floor ceil trunc
  int round min max hypot factorial comb perm gcd lcm`.
  Everything else (names, attributes, strings, lists, lambdas, comprehensions, comparisons, f-strings, other calls)
  is refused with a clear message.
- Exact numbers: integers are exact big integers; `int / int` is an exact fraction (shown as `7/2 (= 3.5)`);
  floats and functions like `sin` give 15 significant digits.
- Limits: 500 characters, 250 tree nodes, depth 40, results up to about 4,200 digits, exponent <= 10,000,
  factorial <= 2,000, comb/perm <= 5,000, 2 s wall clock, at most 10 expressions per call. Division by zero, overflow,
  NaN/infinity, complex results and bad input return an error text, never an exception.
- Risk level READ: no file/network/system access, no approval. Its result is not "untrusted", so it does not taint the
  session.
- Offered only when relevant (see routing), or when you name it: `calc.evaluate`, `@calc`, `/calc.evaluate 2+2`,
  `/tool calc.evaluate expression="2^10"`.
- **Pre-calculation:** arithmetic written in your message (`What is 17*23+45/9-3?`) is calculated by the application
  before the model runs and handed over as `[Calculator results ...]`. Dates, times, versions, ranges (`10-20`),
  `4x`, the tail of `x^2*4` and pieces of function calls are deliberately skipped.

### Routing (`route_message`)
Returns a structured `Route`: tools offered, memory lookup yes/no, complexity (score + reasons), pre-calculated
results, and why the calculator was offered. Complexity is a score; **3 or more is "complex"**. Signals (examples):
analysis/design/debug wording +3, code block +2, debugging code +2, input/output examples +2, problem constraints
(`n <= 10^5`, test cases) +2, coding task +1, algorithmic topic +1, many arithmetic operations +1..+3, an equation +2,
a word problem with 3-4+ values +2..+3, numbered/ordered multi-step instructions +2, several conditions +2, long
message +1..+3. Dates, times, phone-like numbers, versions and plain numbers add nothing. A short message can be complex;
a message with numbers is not automatically complex. Only the text you typed is examined, only its first 6,000
characters, and routing costs about 2 ms.
Calculator offered for: arithmetic in the message, calculation wording with a number, a numerical programming
problem (I/O examples or constraints plus numbers), a word problem with several values, or naming it.

### Choosing the chip (`ChipManager.choose`)
1. A pending `/use` override wins (and is consumed).
2. Otherwise: complex + Advanced configured + `performance_priority` allows (`balanced`: complex only; `quality`:
   always; `speed`: never) + `auto_escalation` on + RAM fits -> Advanced; anything else -> Basic.
3. If Advanced was wanted but is not used, `/why` says why (not configured, speed priority, escalation off, RAM,
   load failed). Ordinary conversation stays on Basic.
The result is a `ChipChoice` (chip, mode auto/manual, reason, note, error). The chip is fixed for a turn; the tool loop
asks `_chip_for_step()` for every step and records it, which is where future mid-task escalation will plug in.

### Working method for numbers (instructions, only when the calculator is offered)
Restate -> list values and conditions -> write expressions -> `calc.evaluate` (batched) -> read results -> check
consistency -> answer. Numbers must be labelled: **calculated** (from `calc.evaluate`), **estimated** (the model's own
arithmetic), **tested** (code actually run). Ksar cannot run code, so it must never claim to have tested anything.

### Diagnostics
- Footer after each answer: `(Basic qwen3:8b · auto · 120 tokens, 7.4 tok/s · calc: 1/1 calls ok)`.
- `/why`: chip, mode, reason, note, complexity score and signals, tools offered, calculator use, every tool call and
  whether it succeeded, steps, time.
- `ksar_data/logs/routing.jsonl`: one JSON line per chat turn. Tool calls also stay in `audit.jsonl`.

## How to use
```
/use advanced        # next message only
/use basic           # next message only (alias of standard)
/use auto            # clear any pending choice
/use status          # current mode / pending choice
/why                 # explain the last answer
What is 17*23+45/9-3?                     # pre-calculated, no tool round-trip needed
A train goes 120 km in 1.5 h, then 90 km in 2 h. Average speed?   # calculator is offered, Basic or Advanced by routing
/calc.evaluate 2^10 ; sqrt(144) ; factorial(20)     # run the calculator yourself, no model
/tool calc.evaluate expression="12*(3+4)/5"
```

## Limitations
- The calculator checks arithmetic, not reasoning: the model must still set up the right expressions. Results are
  trustworthy; the answer built on them is only as good as the model.
- No code execution (deliberately): "tested" is never true. A sandboxed runner needs its own security design (next major update).
- Routing is heuristic. Unusual phrasing can be missed. Force it with `/use advanced` or name `@calc`.
- `/use` applies to chat messages, not to `/task` runs (tasks route automatically).
- Plain `x`-algebra (`3x+7=22`) is not solved by the calculator (no symbols); the model reasons, the calculator checks values.
- Verification is by instructions plus exact results; there is no automatic re-check of the final answer yet.
- Not verified against a real Ollama in the build environment (fake model and fake HTTP server only).
